# Protocol Dice Engine — Skill Mastery r001

**Status:** DESIGN AUTHORITY — simulation candidate

## Purpose

Skill Mastery creates an upper-tier expression of expertise without changing the ordinary Protocol Dice pool for beginning and intermediate characters.

## Core rule

A character may gain **Mastery** in an individual Skill when an implementation permits it.

A Mastered Skill has a **Skill Mastery Die** equal to the Skill's current die size.

The Mastery Die is **not rolled automatically**. It enters the pool only when a Feature, condition, stance, item, power, or other implementation-defined access mechanism explicitly permits the character to use Skill Mastery.

When accessed, the Mastery Die is an additional die beyond the normal Skill die. In implementations whose ordinary practical ceiling is five dice, Mastery therefore creates a controlled **six-die pool**.

If the underlying Skill die later improves, its Mastery Die improves to match.

## Design boundary

Mastery belongs to the Protocol Dice Engine. The method of accessing Mastery belongs to the implementation.

Examples: a science-fiction implementation may require an augmentation; fantasy may require a spell, focus, stance, or attunement; espionage may require preparation or an asset; another game may make Mastery intrinsic.

## Power ceiling

Skill Mastery is intended as an upper-tier mechanic. It should not cause routine seven-, eight-, or larger-die escalation. Later advancement should generally broaden access, reduce opportunity cost, or add bounded interactions with Mastery rather than simply adding more dice.

## Opposition

Important adversaries may possess Mastered Skills and an appropriate access mechanism. This provides a common mechanical language for peer-grade opposition without requiring inflated HP or target numbers.

## Simulation requirements

Test frequency of six-die pools, pattern/dice-trick incidence, specialist versus generalist value, effect on success distributions, enemy Mastery, and whether Mastery feels exceptional while still being usable routinely when a character commits resources to it.
